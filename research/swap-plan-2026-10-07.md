# Move Bridge Swaps — ETH ↔ APT cross-chain swap plan (testnet)

Date: 2026-10-07. Model: solver/RFQ auction, Intents-style. Scope: contracts
+ solver service + web UI, testnet only (Ethereum Sepolia/Hoodi + Aptos
testnet). Safety bar: at least as good as NEAR Intents and Stargate —
argued per-property in §5.

## 1. What we're building

A user holding ETH on Ethereum testnet declares "X ETH → APT on Aptos
<address>". A solver quotes a binding Y-out, fills from its own APT
inventory on Aptos, and claims the locked ETH on Ethereum after proving the
fill. Either both legs complete or the user is refunded after a timeout.
No wrapped tokens, no pools, no custody beyond escrow timelocks.

Why RFQ (not pools, not HTLC): pools need seeded liquidity per pair and
rebalancing; HTLCs need both parties online with hash preimages and painful
UX. RFQ puts inventory risk on a professional solver and gives the user a
fill-or-refund guarantee — the Intents-proven shape, scoped to exactly one
pair.

## 2. Architecture

```
Ethereum testnet (escrow)          Solver (off-chain TS)          Aptos testnet (payout)
─────────────────────────          ───────────────────          ─────────────────────────

User ──① lock ETH ──► SwapEscrow.lock(aptosRecipient, minOut, deadline)
         emits SwapLocked(swapId, sender, amount, minOut, deadline)
                         │  ② solver sees event, quotes Y ≥ minOut
                         │  ③ solver sends APT ──► user on Aptos
                         │     (plain transfer from solver inventory)
                         │  ④ solver submits proof ──► SwapEscrow.claim(swapId, aptosTxProof)
                         │     escrow verifies fill, releases ETH to solver
                         │  ──or── timeout: user calls refund(swapId) ──► ETH back
```

Contracts:

- **`contracts/maroo/src/` — `SwapEscrow.sol` (new, separate from
  `OkrwVault.sol`).** `lock(aptosRecipient, minOut, deadline)` payable;
  `claim(swapId, proof)` solver-only, verifies the Aptos fill (v1: solver
  attestation + recorded aptosTxHash with challenge window; see §4 for the
  upgrade to light-client/SPV verification); `refund(swapId)` user-only
  after deadline; `cancel` pre-fill; pause; per-swap and daily caps; replay
  guard per swapId. No admin custody — escrow can only go to solver-on-claim
  or user-on-refund.
- **`contracts/aptos/sources/swap.move` (new, separate from `bridge.move`).**
  v1 needs no escrow on the Aptos side: payout is a plain APT transfer from
  solver inventory to the user (verifiable onchain by tx hash). A future
  reverse direction (APT→ETH) would add a mirror escrow module. v1 scope:
  one direction only (ETH→APT).
- **Solver service (`swap-solver/`, new, TS like `relayer/`).** Watches
  `SwapLocked` events; price check (ETH/USD ÷ APT/USD + spread); sends APT
  on Aptos; submits `claim` with proof; auto-refund sweeper (calls nothing —
  user refunds, solver just stops quoting expired); inventory/position
  monitor + alerting (same pattern as `relayer/src/monitor.ts`); idempotency
  ledger (same pattern as `relayer/data/`).

Web UI: extend `relayer/public/index.html` (or a new `swap/` page): quote
box (amount in → quoted APT out + expiry), swap button (lock tx), status
tracker (locked → filled → claimed / refundable), refund button after
deadline.

## 3. Safety: how each property is enforced

| Property | Enforcement |
|---|---|
| User can't lose principal | Escrow releases only to solver-with-proof or user-on-refund; no admin withdraw path exists |
| Solver can't steal | Claim requires recorded Aptos payout to the exact recipient ≥ minOut; fake proof reverts |
| No double-claim | swapId spent-flag; claim and refund mutually exclusive |
| Stuck funds recoverable | Deadline per swap; permissionless `refund` after expiry (user only, no keeper needed) |
| Replay across swaps | Unique swapId = keccak(sender, nonce); proof bound to swapId |
| Compromised solver key | Solver key holds only inventory + claim rights; cannot touch unfilled escrows or redirect payouts; per-solver daily claim cap |
| Contract bug / pause | `pause()` freezes lock+claim; refunds always available even when paused |
| Oracle/price manipulation | No oracle: solver's quote IS the price; user's minOut is the slippage guard |

## 4. Known limitations (honest)

1. **v1 fill verification is solver-attested**, not trustless: the escrow
   records the solver's claimed Aptos tx and enforces a challenge window
   during which anyone can dispute with a conflicting proof. Full
   trustlessness needs an Aptos light client or ZK proof of the Aptos tx on
   Ethereum — expensive, deferred to v2. This matches Stargate's trust shape
   (attester set) but not Intents' Verifier atomicity.
2. **One direction only** (ETH→APT). Reverse needs the mirror escrow on
   Aptos + ETH inventory — same pattern, second build.
3. **One solver (ours).** No auction competition in v1, so no price
   discovery — quotes are cost-plus. The RFQ *interface* (quote → commit →
   fill) is built auction-ready (multi-solver quote selection is a service-
   layer addition, no contract change).
4. **Testnet only.** No real funds, no audit. Mainnet needs 2+ audits,
   solver bonding/staking, and the v2 verification upgrade.

## 5. Safety comparison: us vs NEAR Intents vs Stargate

| Property | Move Bridge Swaps (v1) | NEAR Intents | Stargate (LZ) |
|---|---|---|---|
| User principal safety | Escrow + refund; no admin path — **equal** | Verifier fill-or-refund — reference | Pool withdraw / guaranteed NSM Resolution — reference |
| Fill verification | Solver-attested + challenge window — **weaker** | Verifier atomicity on NEAR L1 — stronger | DVN quorum on messages — stronger |
| Counterparty trust | 1 solver key (inventory + claim only) — **narrower blast radius, less decentralized** | Solver market (competition) + MPC + bridge per route | App-chosen DVN set; 1 executor/path |
| Settlement dependency | Ethereum finality + Aptos tx honesty | NEAR L1 + MPC + withdrawal bridge (proven hackable: $3.8M BSC Oct 2026) | LZ messaging + destination pools |
| Admin/custody risk | None by construction (no withdraw) — **strongest** | Foundation-seeded solvers, hosted 1Click | LZ Labs default executor + Stargate Labs pools |
| Audit maturity | Zero (new code) — **weakest** | Audited, live $4.4b/mo | Audited, live $992m/mo |
| Direction | ETH→APT only | ~35 chains, any quoted asset | EVM + non-EVM OFT peers |

Verdict: v1 matches both on the property that matters most for user funds
(no-loss escrow + refund), beats both on admin-custody risk (nothing to
steal), and trails both on verification decentralization and audit maturity.
"At least as good" holds for fund safety; not yet for trust minimization —
that gap is exactly the v2 light-client upgrade + multi-solver auction.

## 8. v2 upgrades (built 2026-10-07): multi-solver auction + committee verification

Honest finding first: a true ZK/consensus light client verifying Aptos fills
on Ethereum does not exist as production tooling (no AptosBFT Ed25519 EVM
verifier; no ZK bridge documents Aptos→EVM; Wormhole Queries is committee
attestation, not consensus verification). So v2 implements what production
actually uses — bonded competition + M-of-N committee attestation — and
keeps the no-admin-withdraw guarantee throughout.

- `contracts/maroo/src/SwapAuction.sol` — bonded solver registration,
  per-swap on-chain quotes (improve-only, minOut floor), anyone-finalizes
  best-quote-wins, `reportDefault` slashes `defaultCompensation` from the
  winner's bond to the user (one-shot). `SwapAuction.t.sol`: 12 tests.
- `contracts/maroo/src/FillAttester.sol` — M-of-N EIP-712 `Fill` committee
  (inline EIP-712/ecrecover, no OZ dep; sorted-sig stack-safe verification;
  replay-consuming digests binding chainId+escrow+swapId). Attester set +
  threshold admin-managed with removal floor. `FillAttester.t.sol`:
  11 tests (real `vm.sign` signatures, threshold/duplicate/unsorted/
  non-member/replay/chain-binding cases).
- `SwapEscrow.claimAttested` — committee path settles immediately (no
  challenge window); solver path unchanged for liveness. `setFillAttester`
  (zero disables). Shared `_checkFill` preconditions for both paths.
- `SwapV2E2E.t.sol` — full v2 flow: lock → quotes → finalize (B wins) →
  attested claim → immediate settle; plus solver-path liveness.
- `foundry.toml`: `via_ir = true` (legacy codegen stack-too-deep on the new
  contracts; compiler-recommended fix).
- Solver: auction-aware (`SWAP_AUCTION_ADDRESS` set = notify+quote, fill
  only after winning; unset = v1 direct-fill preserved). Attester-path claim
  submission is contract-ready; solver-side EIP-712 attester coordination
  (collecting off-chain committee sigs) is the remaining integration step.
- Results: **forge 72/72 · swap-TS 4/4 · relayer-TS 23/23 · move 17/17.**
- Safety delta vs §5: single-solver-key theft eliminated on the attested
  path (needs M-of-N attester collusion + winner); winner default now costs
  bond (compensation to user); auction gives price competition. Remaining
  gap to Intents/Stargate: attester set is still admin-appointed (not a
  permissionless validator set), contracts unaudited.

## 9. v3: genuine Aptos light client on EVM (built 2026-10-08)

Why: v2's committee attestation is operator trust, not cryptographic proof.
v3 verifies REAL Aptos BFT artifacts on-chain: a validator-set-anchored QC
(aggregate BLS over `seed||BCS(LedgerInfo)`) plus a transaction-accumulator
inclusion proof for the fill. All cryptography pinned against aptos-core
sources plus noble-curves oracles (POP DST, `{DST}` object form).

- `contracts/maroo/src/BlsAptos.sol` — POP-DST BLS12-381 over EIP-2537
  precompiles: `signingMessage` (seed `98274d3a…e1fbaa2` =
  `SHA3-256("APTOS::LedgerInfo")`), IETF `hashToG2` (XMD:SHA-256, count=2,
  m=2, L=64; modexp-reduced limbs; MAP_FP2_TO_G2 + G2ADD), `verifyAggregate`
  (pairing equation `e(-PK,H)·e(G1,sig)==1`), `aggregateG1` (G1MSM).
  `BlsAptos.t.sol`: 8 tests incl. oracle aggregate verification + tampered-sig
  rejection. Three REAL bugs found by oracle testing (not codegen): modexp
  input 224 vs 240/256 bytes, Fermat-inverse-instead-of-reduction exponent,
  XMD `I2OSP(0)`-vs-`l_i_b_str` first-block input.
- `contracts/maroo/src/Sha3.sol` — NIST SHA3-256 from scratch (NOT keccak;
  Aptos hashes are NIST-padded). 5 NIST vectors + keccak-divergence test.
- `contracts/maroo/src/AptosLightClient.sol` — anchored committee (epoch,
  compressed G1 keys, powers; quorum = total·2/3+1 exactly like
  aptos-core `ValidatorVerifier::new`): `anchor`, `submitQC` (bitmask
  subset + G1/G2 decompression + aggregate verify + staleness gate),
  `verifyQC` (stateless), `advanceEpoch` (rotation QC under the OLD set +
  embedded next-epoch-state byte-match), `verifyInclusion` (accumulator
  fold, depth ≤ 63; `fold1` public per-level frame), `parseLedgerInfo`
  (129-byte no-rotation BCS). `AptosLightClient.t.sol`: 25 tests (happy
  path, all gates' negatives, tampered sig/BCS).
- `SwapEscrow.claimProven` — trustless settlement: verifies inclusion under
  `latestRoot`, binds auction winner (`swapAuction.winner(swapId)`) when set,
  settles immediately (no challenge window). `setLightClient`/`setSwapAuction`
  (zero disables each path). `SwapProvenE2E.t.sol`: 5 tests (full path,
  wrong-winner, no-auction, wrong-leaf, no-LC).
- `swap/src/lc-oracle.mjs` — deterministic QC+inclusion vector generator
  (committee sk 1..7, epoch-58 LedgerInfo, signers [0..4]); `swap/src/prover.ts`
  — `fillLeafHash`/`foldInclusion`/`claimProvenArgs` (self-checks fold vs QC
  root)/`parseLedgerInfo`; `swap/test/prover.test.ts`: 5 tests.
- via_ir-nightly rules learned (bugs that LOOK like codegen, most diagnosed
  by isolated-probe bisection): `.length` reads on deep buffers, early
  returns, parameterized buffer offsets, nested helper args, uint8 stack
  hoists, sequential copy loops (encodePacked staging instead), state writes
  after deep buffer flow, storage array-of-bytes snapshots. One REAL
  constant bug caught late: `(p+1)/2` literal missing its leading zero
  nibble (`0d00…` → `d00…`), flipping the G1 sort for oracle K3 only —
  pinned by the 5-key QC + per-key leaf hashes.
- Regen: `node swap/src/lc-oracle.mjs` → `/tmp/lc-vec.json` (QC vectors);
  e2e QC: committee script + fill-leaf QC script (see §9 source notes) →
  `/tmp/e2e-qc.json`. Oracle values are ALSO pasted into the .t.sol files
  so `forge test` needs no network.
- Results: **forge 114/114 · swap-TS 9/9** (4 existing + 5 prover).
- Trust delta vs §8: proven path needs NO committee honesty (only the
  anchored set + Aptos BFT); anchor rotation is admin-set checkpoint trust
  (same as any light-client checkpoint), one-way epoch ratchet.
  Remaining: contracts unaudited; anchor should move to governance/multisig.
