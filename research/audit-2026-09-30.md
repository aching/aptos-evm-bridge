# Security audit — OKRW bridge (2026-09-30)

Scope: `contracts/maroo/src/OkrwVault.sol`, `contracts/aptos/sources/okrw.move`,
`contracts/aptos/sources/bridge.move` (+ tests). Off-chain relayer/server
reviewed for interface assumptions only.

Trust model (accepted, demo): single trusted relayer key holds the Aptos
MintRef and the Maroo release right. A compromised relayer can mint up to the
daily cap and release up to the daily cap. All findings below assume this
model and harden everything around it.

## Findings fixed

| # | Severity | Location | Issue | Fix |
|---|----------|----------|-------|-----|
| 1 | High | bridge.move | `Config.relayer` immutable — key compromise unrecoverable; redeploy would wipe replay history | Two-step `propose_relayer` / `claim_relayer` (claim proves key ownership by signing); Config+Seen move together so nonces can never re-mint. Tested incl. replay-after-rotation rejection |
| 2 | Med | bridge.move | `metadata` caller-supplied — compromised relayer could mint a lookalike coin | `Config.metadata` pinned at `init`; asserted in `mint_attested` + `burn_withdraw` (`EWRONG_METADATA`). Tested with a genuine second FA |
| 3 | Med | bridge.move | `burn_withdraw` trusted a caller-supplied `bridge_addr` while `mint_attested` derived it from the signer | Canonical: both derive from relayer signer; param removed; TS callers updated |
| 4 | Med | okrw.move | `bridge_burn` ignored pause (mint was blocked) — inconsistent incident response | Fail-closed: `bridge_burn` asserts `!paused`. Tested |
| 5 | Med | okrw.move | Only `minter` rotatable; lost pauser/denylister/admin keys brick controls | `set_pauser`, `set_denylister`, two-step `propose_admin`/`accept_admin` (accept proves key ownership). Tested incl. accept-without-proposal rejection |
| 6 | Med | OkrwVault.sol | No reentrancy guard on `release` (safe today via CEI, fragile to future edits) | `nonReentrant` mutex. Tested with a malicious reentering recipient contract |
| 7 | Med | OkrwVault.sol | Single EOA admin, no rotation; key loss freezes pause/relayer/cap | Two-step `proposeAdmin`/`acceptAdmin`. Tested incl. wrong-claimant rejection |
| 8 | Low | bridge.move | Magic abort code `6` for bad recipient | Named `EBAD_RECIPIENT`; added `RelayerRotated`, `DailyMintCapUpdated`, `RoleUpdated` events for transparency |

## Residual accepted risks

1. Single trusted relayer (demo model). Production: N-of-M attester set,
   on-chain signature verification in `mint_attested`.
2. Strict release-nonce ordering can stall liveness if one release is
   cap-blocked (safety > liveness; operator retries next window).
3. `Seen.attested` is an unbounded vector (O(n) replay checks) — fine at demo
   volume; production should use a nonce watermark or Table.
4. No light-client verification of Maroo state on Aptos (relayer attests).
5. Server holds all demo keys (`relayer/.env`, gitignored, testnet-only).
   Never reuse this pattern with real value.
6. Maroo-side recovery if Aptos halts: relayer can still `release` manually
   to original depositors (no on-chain proof required) — operator procedure,
   not code.
